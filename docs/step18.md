# 단계 18: 응답 캐싱의 TTL 엣지 케이스 10개

단계 17의 기본 캐싱에서 "아직 다루지 않은 것"으로 적어 둔 경우들이다. 경우마다 무엇이 문제인지, 어떻게 했는지, 무엇으로 확인했는지를 적는다. 9번과 10번은 코드 리뷰에서 나온 경우다.

## 바뀐 구조

| 무엇 | 단계 17 | 단계 18 |
|---|---|---|
| 사본의 시각 칸 | `saved_at`(저장한 시각)으로 만료를, `last_used`(마지막으로 쓴 시각)로 LRU를 판단 | `expire_at`(만료 시각 = 백엔드에 물어본 시각 + TTL)과 `last_used`(마지막으로 쓴 순번) |
| `cache_put` | 저장한 지금부터 TTL을 센다. 항상 덮어쓴다 | 백엔드에 물어본 시각(`fetched_at`)을 받는다. 더 늦게 물어본 사본은 덮어쓰지 않는다 |
| 시계 | `cache.c` 안에서 `CLOCK_MONOTONIC`을 직접 읽음 | `cache_clock` 함수 포인터로 읽는다. 테스트가 바꿔 낄 수 있다 |
| 버릴 사본 | 가장 오래 쓰지 않은 사본 | 만료된 사본 먼저, 그다음 가장 오래 쓰지 않은 사본 |

## 엣지 케이스 10개

| 번호 | 경우 | 대응 | 코드 | 확인 |
|---|---|---|---|---|
| 1 | 경계: 만료 시각 "딱 그 순간"은 만료인가 | `expire_at = 백엔드에 물어본 때 + TTL`로 저장하고, `지금 >= expire_at`이면 만료다 | `cache_put`, `cache_get` | 테스트 "엣지 1": 1밀리초 전은 hit, 그 순간은 miss |
| 2 | 지연 삭제: 만료된 사본은 언제 지우나 | 따로 지우는 스레드를 두지 않는다. 찾았는데 만료면 그 자리에서 지우고 miss로 처리한다. miss 뒤 저장이 새 사본을 넣는다 | `cache_get` | 테스트 "엣지 2": 찾기 전에는 메모리에 남아 있고, 찾으면 지워진다 |
| 3 | 확인과 교체 사이 끼어들기: A가 만료를 보고 잠금을 푼 사이 B가 새 사본을 넣는다 | 만료 확인과 삭제를 같은 잠금 구간에서 한다. 저장할 때는 앞에서 본 것을 믿지 않고 잠금 안에서 키로 다시 찾아 바꾼다 | `cache_get`, `cache_put` | 테스트 "엣지 3" 두 개: 차례로 저장해도 사본은 하나, 스레드 넷이 동시에 해도 내용이 깨지지 않음(`make asan`으로도 실행) |
| 4 | hit이 수명을 늘리는가 | 늘리지 않는다. hit은 `last_used`만 바꾸고, `expire_at`은 저장할 때만 정한다. 단계 17에서 `saved_at`으로 이미 나눠 두었고, 여기서는 테스트로 확인한다 | `cache_get` | 테스트 "엣지 4": 만료 직전에 hit해도 만료 시각에 miss |
| 5 | 10초를 기다리지 않고 만료를 테스트하려면 | 캐시가 시각을 `cache_clock` 함수 포인터로 읽는다. 테스트는 원하는 시각을 돌려주는 `fake_now`로 바꾼다 | `cache.h`의 `cache_clock`, `tests/test_proxy.c`의 `fake_now` | 위 테스트들이 기다리지 않고 실행된다 |
| 6 | 자리가 모자랄 때 무엇을 먼저 버리나 | 만료된 사본을 먼저 버린다. 어차피 다시 쓰이지 않을 사본이다. 없으면 가장 오래 쓰지 않은 사본 | `pick_victim` | 테스트 "엣지 6": 가장 최근에 썼지만 만료된 사본이 버려지고, 가장 오래 쓰지 않은 사본은 남는다 |
| 7 | 캐시 스탬피드: 사본이 없을 때 같은 요청이 동시에 온다 | 그대로 둔다. 모두 miss해서 백엔드에 가고, 백엔드의 내용이 그대로면 응답은 모두 올바르다. 가장 늦게 물어본 사본 하나만 남는다(9번) | (바꾸지 않음) | `tests/run_proxy_tests.sh`: 동시 요청 5개가 모두 올바른 응답을 받음. 기록된 값: 5개 모두 miss |
| 8 | TTL이 사본을 새것으로 바꾸는 유일한 수단이다 | TTL을 10초로 정했다. 백엔드의 내용이 바뀌어도 최대 10초 동안 예전 사본을 보낸다 | `cache.h`의 `CACHE_TTL_MS` | 단계 17의 테스트: 백엔드 파일을 바꿔도 사본을 받음 |
| 9 | 먼저 물어보고 늦게 끝난 응답: A가 miss를 보고 느린 백엔드에 물어본 사이 내용이 바뀌고, B가 새 내용을 먼저 저장한다. A가 뒤늦게 옛 내용을 저장하러 온다 | 프록시 프로세스가 miss를 본 시각을 `cache_put`에 넘긴다. 있는 사본의 `expire_at`이 더 늦으면(더 늦게 물어본 응답이면) 덮어쓰지 않는다 | `proxy/proxy.c`의 `asked_at`, `cache_put` | 테스트 "엣지 9": A의 저장이 0을 돌려주고 B의 사본이 남는다 |
| 10 | TTL을 어디서부터 세나: 3초 걸려 받은 응답을 저장한 때부터 10초 쓰면 내용은 최대 13초 낡는다 | 만료 시각을 물어본 때부터 센다. 받는 데 TTL보다 오래 걸린 응답은 저장하지 않는다 | `cache_put` | 테스트 "엣지 10" 두 개 |

## 내린 결정과 이유

| 결정 | 이유 |
|---|---|
| 3번은 단계 17부터 잠금 안에서 찾고 저장하게 해 두었다 | 잠금을 푼 뒤 앞에서 본 사본의 포인터를 쓰면, 다른 스레드가 이미 해제한 메모리를 읽어 프록시 프로세스가 죽을 수 있다. 다른 경우는 빠져도 "덜 좋은 동작"이지만 이것은 다르다 |
| 7번 스탬피드는 막지 않는다 | 막으려면 "이 키는 지금 누가 가져오는 중"이라는 상태와, 다른 스레드를 기다리게 하는 방법(조건 변수)이 필요하다. 응답이 틀리는 것은 아니라서 넣지 않았다 |
| 9번과 10번을 순번(세대 번호) 대신 시각 하나로 풀었다 | 물어본 시각을 넘기면 "누가 더 새로운가"(9번)와 "언제 만료되나"(10번)가 같은 값으로 정해진다. 칸을 더 두지 않아도 된다 |
| TTL 10초 | 시연에서 hit과 만료를 한 장면에 볼 수 있다. 길게 잡을수록 백엔드에 덜 가지만 예전 내용을 오래 보낸다 |
| `last_used`는 시각이 아니라 순번 | 같은 밀리초에 쓰인 사본들의 순서도 구분된다 |

## 테스트

```bash
make test    # "엣지 1" ~ "엣지 10" 줄과 "동시에 온 같은 요청 5개" 줄
make asan    # 같은 테스트를 메모리 오류 검사와 함께
```

`hammer` 테스트(스레드 넷)는 데이터 레이스 검사로도 확인했다. 경고가 없어야 한다.

```bash
gcc -Wall -Wextra -std=c11 -g -pthread -Iinclude -Iproxy -fsanitize=thread proxy/proxy.c proxy/cache.c $(ls src/*.c | grep -v main.c) tests/test_proxy.c -o build/test_proxy-tsan && build/test_proxy-tsan
```

## 한계

- 만료된 사본은 누가 찾거나 자리가 모자랄 때까지 메모리에 남는다 (최대 1 MiB).
- 스탬피드: 사본이 없는 순간에 같은 요청이 N개 오면 백엔드가 N번 일한다.
- 9번은 같은 밀리초에 물어본 두 응답의 순서를 구분하지 못한다. 그때는 나중에 저장한 것이 남는다.
