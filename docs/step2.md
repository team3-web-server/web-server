## 실행 결과

터미널 A에서 `./build/server`, 터미널 B에서 `curl localhost:8080/index.html`을 실행했을 때 A의 출력:

```
socket fd = 3
bind 성공: 0.0.0.0:8080
listen 중: 연결을 기다립니다 (다른 터미널에서 curl localhost:8080)
연결 수락: 클라이언트 127.0.0.1:41936 (conn fd = 4)
받은 바이트 수: 87
메서드: GET
요청 대상: /index.html
버전: HTTP/1.1
연결을 닫았습니다 (conn fd = 4)
```

B의 출력: `curl: (52) Empty reply from server` (응답을 아직 보내지 않기 때문)

## 중요하다고 본 개념

### 요청 줄의 형식

RFC 9112 3절의 정의:

```
request-line = method SP request-target SP HTTP-version
```

- `SP`는 공백 한 글자(0x20), 줄 끝은 `CRLF`(`\r\n`, 0x0D 0x0A) 두 글자다.
- `curl localhost:8080/index.html`이 보내는 요청은 87바이트이고, 첫 줄 `GET /index.html HTTP/1.1`은 24바이트 + CRLF 2바이트다.

```
G E T ␠ / i n d e x . h t m l ␠ H T T P / 1 . 1 \r \n
└─┬─┘   └────────┬─────────┘   └──────┬──────┘
메서드(3)    요청 대상(11)          버전(8)
```

### 파서가 하는 일 (순서대로)

1. `strstr(buf, "\r\n")`로 첫 줄의 끝을 찾는다. 없으면 실패.
2. `memchr`로 줄 안에서 첫 번째 공백을 찾는다. 그 앞이 메서드.
3. 그 다음 글자부터 줄 끝까지에서 두 번째 공백을 찾는다. 두 공백 사이가 요청 대상.
4. 두 번째 공백 다음부터 줄 끝까지가 버전. 여기에 공백이 또 있으면 실패.
5. 세 칸의 길이를 구한다. 빈 칸이 있으면 실패. 여기까지는 아무것도 할당하지 않는다.
6. 칸마다 `malloc(길이 + 1)`로 할당해 `memcpy`로 복사하고 끝에 `'\0'`을 붙인다. 하나라도 할당에 실패하면 이미 할당한 칸을 해제하고 실패.

`memchr`에 "줄 끝까지의 길이"를 주는 이유: `strchr`처럼 문자열 끝까지 찾으면 첫 줄에 공백이 없을 때 다음 줄(`Host: localhost`)의 공백을 잡아 버린다.

### `read()`와 `'\0'`

- `read(fd, buf, n)`은 받은 바이트를 `buf`에 복사하고 **복사한 바이트 수**를 돌려준다. 끝에 `'\0'`을 붙여 주지 않는다.
- `strstr` 같은 C 문자열 함수는 `'\0'`을 만날 때까지 읽는다. 그래서 `buf[n] = '\0'`을 직접 넣어야 하고, 그 자리를 남기려고 `read`에 `sizeof(buf) - 1`을 준다.
- 반환값 0은 상대가 아무것도 보내지 않고 연결을 닫았다는 뜻, -1은 에러다.

### `malloc`과 `free`

- `malloc(n)`은 힙에서 n바이트를 할당하고 시작 주소를 돌려준다. 실패하면 `NULL`. 함수가 끝나도 사라지지 않고, `free`로 해제할 때까지 남아 있다.
- 할당한 쪽과 해제하는 쪽의 약속: `parse_request_line`이 0을 돌려주면 호출한 쪽이 `free_request`를 불러야 한다. -1이면 세 포인터가 모두 `NULL`이고 해제할 것이 없다.
- 해제를 빠뜨리면 메모리 누수다. `make asan`(`-fsanitize=address,leak`)이 프로그램이 끝날 때 해제되지 않은 할당을 보고한다.
- `free_request`는 해제한 뒤 포인터를 `NULL`로 바꾼다. `free(NULL)`은 아무 일도 하지 않으므로, 두 번 불러도 같은 주소를 두 번 해제(이중 해제)하지 않는다.

## 결정사항과 이유

| 결정 | 이유 |
|---|---|
| 각 칸을 `malloc`으로 필요한 길이만큼 할당해 복사 | 클라이언트가 요청을 얼마나 길게 보낼지 미리 알 수 없으므로, 파서 쪽에 고정된 길이 제한(예: `target[1024]`)을 두고 싶지 않았다. 칸 길이만큼만 할당하므로 구조체는 포인터 세 개(24바이트)이고, 읽기 버퍼를 나중에 키워도 파서는 고칠 것이 없다. 입력 `buf`를 바꾸지 않고(`const char *`) 결과가 `buf`와 따로 있어서 `buf`를 재사용해도 안전하다. 대신 `malloc` 실패 처리와 `free_request` 호출을 빠뜨리지 않아야 한다. 주의: 파서의 제한은 없어졌지만 `main.c`의 읽기 버퍼(4096바이트)에 들어온 만큼만 파싱되므로, 지금 서버가 실제로 받는 요청 줄의 상한은 4095바이트다 |
| 실패하면 `req`의 세 포인터를 모두 `NULL`로 둔다 | 실패 뒤에 실수로 `free_request`를 불러도 안전하고, 쓰레기 주소를 읽는 일이 없다 |
| 공백이 정확히 두 개일 때만 성공 | RFC 형식 그대로다. 공백 여러 개나 탭을 허용하는 느슨한 해석은 하지 않는다 |
| 줄 끝은 CRLF만 인정 (LF만 있으면 실패) | RFC 형식 그대로다 |
| 실패는 모두 -1 하나로 돌려준다 | 실패 종류를 구분해 400·414 같은 응답을 고르는 것은 단계 5 범위다 |
| 메서드가 `GET`인지, 버전이 `HTTP/1.1`인지 검사하지 않는다 | 이번 단계는 "나누기"까지다. 지원하지 않는 메서드를 거절하는 것은 단계 5 |
| `main.c`에서 `read()`를 한 번만 부른다 | 파서가 실제 `curl` 요청에 동작하는 것을 보기 위한 최소한이다. 빈 줄까지 반복해서 읽는 것은 단계 3 |

## 확인한 것

- `make`: 경고 없음 (`-Wall -Wextra`)
- `make test`, `make asan`: PASS 42줄 (서버 2 + `test_net` 15 + `test_http` 25). `make asan`에서 누수 보고 없음
- `valgrind --leak-check=full`로 `build/test_http`와 `build/server`(curl 요청 1개): 에러와 누수 없음
- 누수 검사가 실제로 동작하는지: `main.c`에서 `free_request` 호출을 지운 복사본을 asan으로 빌드해 요청을 보내면 `LeakSanitizer: detected memory leaks ... 3 allocation(s)`로 종료 코드 1이 나왔다
- `curl localhost:8080/index.html` 6번: 6번 모두 서버가 세 칸을 출력하고 `curl`은 `(52) Empty reply from server`. 1-3에서는 요청을 읽지 않고 닫아서 `(56) Connection reset by peer`가 나오기도 했는데, 이제 받은 데이터를 다 읽은 뒤 닫으므로 FIN이 나간다
- `printf 'hello\r\n' > /dev/tcp/127.0.0.1/8080`: `요청 줄 형식이 맞지 않습니다`
- 아무것도 보내지 않고 연결만 닫기: `요청 없이 연결이 닫혔습니다`

(위는 작업 환경인 리눅스 컨테이너에서 확인한 결과다.)

## 아직 하지 않은 것 (알고 있는 한계)

- `malloc`이 실패하는 경로(이미 할당한 칸을 해제하고 -1)는 코드로만 있고 테스트하지 못했다. 메모리 부족을 일부러 만들기 어렵기 때문이다.
- 칸 길이에 상한이 없지만, 실제로는 `main.c`의 읽기 버퍼(4096바이트)에 들어온 만큼만 파싱된다. 너무 긴 요청 줄을 414로 거절하는 것은 단계 5.
- `read`를 한 번만 부른다. TCP는 바이트의 흐름이라 요청이 여러 조각으로 나뉘어 도착할 수 있고, 그러면 첫 `read`에 요청 줄이 다 들어 있지 않아 "형식이 맞지 않습니다"가 나올 수 있다. 단계 3에서 빈 줄(`\r\n\r\n`)까지 반복해서 읽는다.
- 받은 데이터 중간에 0x00 바이트가 있으면 `strstr`이 거기서 멈춘다. 정상 HTTP 요청 줄에는 0x00이 없다.
- 응답을 보내지 않는다 (단계 3).
- 헤더(`Host:` 등)는 해석하지 않는다 (단계 3).
- 형식이 틀린 요청에 400을 보내거나, 메서드를 검사해 405·501을 보내지 않는다 (단계 5).
